# SaaS Project Management Platform

## Complete Development & Continuation Reference

> **Purpose:** This document is the master reference for building a portfolio-grade, production-style SaaS Project Management Platform from scratch.

---

# 1. Project Overview

## Project Name

**SaaS Project Management Platform**

## Project Goal

Build a multi-tenant project management platform where organizations can:

* Create organizations
* Invite/manage members
* Create projects
* Assign project members
* Create and manage tasks
* Assign tasks to users
* Track task status and priority
* Add comments
* Upload attachments
* Receive notifications
* Get real-time updates
* Search and filter tasks
* View activity/audit logs
* Use dashboards and reports

The project should demonstrate professional backend, frontend, database, security, testing, real-time communication, caching, background processing, CI/CD, and deployment skills.

# 5. Development Philosophy

The project will NOT be built by completing the entire backend first and then suddenly starting the frontend.

Instead, use **vertical feature development**.

For each major feature:

```text
Database
   ↓
Domain
   ↓
Application
   ↓
Infrastructure
   ↓
API
   ↓
Swagger Testing
   ↓
Unit/Integration Tests
   ↓
React UI
   ↓
Frontend ↔ Backend Integration
   ↓
Documentation
   ↓
Git Commit
   ↓

```

This approach makes the project easier to debug and keeps every feature functional.

# 7. Core Application Concept

The application is a **multi-tenant SaaS project management platform**.

A user can belong to multiple organizations.

Example:

```text
User A
 ├── Organization X → Owner
 ├── Organization Y → Manager
 └── Organization Z → Member
```

Therefore, authorization must consider:

```text
User
+
Organization
+
Role
+
Resource
```

The frontend must never be responsible for security decisions.

The backend must enforce authorization.

# 23. API Design Rules

Always use DTOs.

Do not directly expose EF Core entities.

Example:

```text
Entity
    ↓
Service
    ↓
DTO
    ↓
Controller
    ↓
Client
```

Use consistent HTTP responses.

Important status codes:

```text
200 OK
201 Created
204 No Content
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Validation Error
500 Internal Server Error
```

# 24. Security Requirements

The application should implement:

* Password hashing
* JWT authentication
* Refresh token rotation
* Secure JWT secret
* HTTPS
* CORS
* Authorization policies
* Organization-level authorization
* Input validation
* Rate limiting
* Secure file uploads
* File size restrictions
* No secrets committed to Git
* Safe exception handling
* Sensitive information excluded from logs

Never put:

```text
JWT secret
Database password
API keys
Private credentials
```

inside GitHub.

# 49. Phase 20 — Redis

Use Redis for appropriate caching.

Potential cache targets:

```text
Organization summaries
Project summaries
Dashboard statistics
Frequently accessed configuration
```

Use cache-aside strategy:

```text
Request
 ↓
Check Redis
 ↓
If found → return
 ↓
If not found
 ↓
Query PostgreSQL
 ↓
Store in Redis
 ↓
Return
```

Invalidate cache after relevant changes.

Do not blindly cache every API endpoint.

Commit:

```text
feat(cache): implement Redis caching
```

# 68. Important Project Rules

## Rule 1

Do not jump ahead.

Complete the current phase before starting the next one.

## Rule 2

Do not write unnecessary code.

Every piece of code should have a purpose.

## Rule 3

Do not expose EF entities directly.

Always use DTOs.

## Rule 4

Do not trust frontend authorization.

The backend must enforce permissions.

## Rule 5

Do not commit secrets.

Use environment variables.

## Rule 6

Test every feature.

Do not assume that successful compilation means the feature works.

## Rule 7

Use PostgreSQL properly.

Use relationships, indexes, constraints, and migrations.

## Rule 8

Use Bootstrap for frontend styling.

Do not introduce Tailwind.

## Rule 9

Do not introduce Docker.

This project intentionally does not use Docker or Docker Compose.

## Rule 10

Commit after every completed functionality.
